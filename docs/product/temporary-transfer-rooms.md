# 临时互传区首版方案

本次确认网页优先、开源自托管、项目方新增费用 0 元。第一条验收路径是两个干净浏览器在同一个站点完成建区、邀请和双向收发，随后用 Windows 客户端加入同一区，再验 Android 浏览器。此文记录产品决定和拟实施的工程步骤。

## 谁提供服务

小组可自行部署站点。运营者决定谁可建区、可使用哪些节点和多少空间。群主提供或选择获准使用的存储和网络。其他成员打开链接即可参加，收件时自行确认保存。提供站点与提供文件副本是两个角色。独立部署须能在没有项目方域名、Cloudflare 账号、Access 或 R2 的条件下完成首个验收流程。Cloudflare 留作可选部署目标。

Windows 保留“发送到设备”的同网直传和逐批确认。另设“发到临时互传区”。由用户选择把文件交给共享节点。第一版围绕临时分享，长期账户、跨账户身份绑定及持续同步留在后续阶段。

## 邀请、权限与撤回

- 建区和加入可以免登录。输入邀请码或打开带 `?code=…` 的链接进入同一区。默认凭限时邀请加入，群主可开启审批。短示例码仅用于说明入口；实现须限制猜码次数和邀请有效期。
- 群主恢复码可用于换设备接管管理权限，与普通邀请分开保管。群主默认最多指定三名管理员。建议支持换发恢复码并使旧码失效。
- 文件默认全区可见，发送前可改为仅指定成员。按钮显示最终接收范围。群主、管理员和发送者可撤下分享。仅指定成员的文件，其明文仅供发送者及被选成员读取；管理权限本身不赋予读取权。
- 撤回和到期使新下载授权失效，供件端停止提供后续数据，接收者已经保存的完整副本归其保留。拟按短期授权分段验证，并测试撤销传播延迟和旧邀请、旧下载链接。无法确认权限的节点暂停分发。指定成员文件的寄存副本按密文设计，须单独验证存储节点无法解密。

## 什么时间能够下载

| 文件状态 | 成员看到的含义 |
| --- | --- |
| 正在准备 | 尚未形成可下载的完整来源。显示进度，保留期尚未起算。 |
| 有人在线即可下载 | 至少一个获准、可达且持有完整文件的节点能供件。显示绝对到期时间。最后一个来源离线时转为等待。 |
| 可离线领取 | 指定常开节点已保存完整副本、校验通过且可访问。日用电脑及其他成员均可离开。常开节点故障时及时降级，已有在线副本仍可供件。 |
| 等待供件设备上线 | 暂无可用来源，保留下载进度及原到期时间。站点本身不可达时，客户端只能提示服务连接中断。 |

首次真正可下载时起算，换源、断网或常开节点后来接手均不重新计时。成员完整下载并校验后，可主动开启或停止协助分发。Windows、NAS、手机均可提供来源。Android 网页首版验收前台供件；锁屏后如来源停止，则续接其他节点，或等来源恢复。

| 单文件大小 | 默认期限 | 手动延期后的累计上限 |
| --- | --- | --- |
| 小于 10 GB | 24 小时 | 72 小时 |
| 10 GB 至 20 GB，含两端 | 6 小时 | 24 小时 |

上限适用于临时区。建议把 GB 明确为十进制字节；建议允许发送者、群主和管理员在现有权限内延期，点击前显示新的到期时间。两项作为实施默认值，保留调整空间。写入常开节点前检查可用存储和配额；拒绝超额的新上传，给既有文件预留完整保留期。公网账单和自托管设备的磁盘、带宽分别核算。

## 复用与实施顺序

1. **先打通最短的网页路径。** 复用现有网页、三套主题、接收确认、WSS 信令与 WebRTC。现有 Worker 以 Access 身份组织设备；拟增加可独立部署的站点服务，隔离既有账户接口与访客房间权限。提供从干净环境启动站点的配置和最小文档。先用小文件跑通双浏览器，验证拒收、邀请审批和权限撤回。
2. **在同一区接入 Windows。** 复用 W1–W3 桌面桥接、受控文件读写与任务状态。同一邀请能在网页或客户端完成加入。保留默认无 LAN 接收监听、确认收件、源文件只读、同名编号。为同一次传输提供稳定文件标识及可查询的逐项收件结果，分别处理恢复旧任务和用户明确再发一份。
3. **再扩展到大文件与协助分发。** 现有网页上限 64 MiB，发送使用整文件 `arrayBuffer()`，接收聚合 Blob 后计算摘要。需要分块读取、持久进度、逐块校验和最终完整性校验。优先实现从一个完整来源续接到另一个来源；并行多源提速可后置。按浏览器文件写入能力和磁盘余量验证上限。20 GB 验收须实际传输完整文件、断线后续传并独立比对落盘 SHA-256。另测 10 GB 边界、超过 20 GB 的预检及到期清理。
4. **最后验 Android 和不同网络。** 以手机浏览器加入同一区，验证选文件、实际保存、哈希、前台供件和锁屏恢复。额外记录不同网络下的直连、常开节点回退和均不可达时的状态。先用隔离环境；公网部署、费用和防火墙变更分别遵守原有授权。

## 测试环境与完成标准

使用两个独立 Windows 客体、独立浏览器配置、工作区与合成素材。优先复用可用虚拟化工具，Windows 镜像取自授权来源，按主机剩余内存、磁盘及图形能力决定是否分批运行 Android。除浏览器对浏览器和浏览器对客户端，还须验证两个 Windows 客户端互收，包括安装包在测试客体上的启动和接续。MSI 安装范围单独记录，虚拟机快照提供回滚。

安卓先评估用户点名的 ApkStart 和官方 Android Emulator 命令行工具。只需要一个能运行浏览器、通过 ADB 检查下载、切换网络及锁屏的客体。实施时固定版本，核验镜像来源与许可、磁盘和加速条件，不随项目再分发系统镜像。[ApkStart 源码](https://github.com/RoutineMiku/apkstart) · [Android Emulator 命令行](https://developer.android.com/studio/run/emulator-commandline) · [QEMU](https://github.com/qemu/qemu) · [Windows 评估镜像](https://www.microsoft.com/en-us/evalcenter/evaluate-windows-11-enterprise)

每个用例记录版本、端点和网络拓扑、预期与实际文件数、字节、SHA-256、任务终态、来源切换与恢复情况。独立虚拟客户机或 Android 模拟器通过实际传输、保存和校验，即记为该场景通过。单进程模拟、同机回环、CI、独立 Windows 客体与 Android 客体分别列证。网页按钮或进度条到达 100% 本身不足以证明落盘。
