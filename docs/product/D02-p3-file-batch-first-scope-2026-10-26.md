## 1. 用户确认原话与取舍

**用户原话：**“D-02 正式选择：A，先单文件 + 多文件批量，文件夹后续实现（推荐）。”

**确认内容：**

- P3 首个可验收的 Windows LAN 传输能力应完成：用户主动选择**单个文件**或**多个普通文件组成的批次**，发送给明确选择的设备；接收方按既有安全策略明确确认。
- 保留 P3 已确定的设备身份、授权、来源保护、可靠加密传输、SHA256 核对、目标路径合法性、同名不覆盖、任务进度/取消、断线失败与恢复入口。**批次允许部分成功，但必须逐文件核算真实终态。**
- **整个目录/文件夹的递归传输不纳入 P3 首版交付与阻塞性验收要求**，包括自动遍历多层子目录、保留原始层级结构、空文件夹重建、递归目录 Copy/同步、符号链接或重解析点穿越。
- 用户直接拖入/选择文件夹时，**不可悄悄展开目录、自动上传全部文件、无提示扁平化处理**。首版应明确说明“暂不支持整个文件夹发送”，引导用户选择具体文件。不能假装已发送目录全部内容。
- 这是阶段取舍，不意味着永远不做文件夹；待单文件/批次真机验收稳定之后，单独设计目录递归、安全约束、失败恢复和 Windows 跨设备场景，再按 Gate 实现。

**选择理由：** 避免 P3 首版同时解决递归复制、复杂目录冲突、重解析链接、深路径和跨平台属性等高风险问题；优先兑现可测、可回滚、不会破坏 P2 数据/文件的最小 LAN 传输闭环。

## 2. P3 首版最小使用流程

1. 在柠猫**已授权文件架/素材列表**中选择单个文件或多选普通文件，使用唯一情境入口“发送到设备”。
2. 设备发现和身份验证必须遵守 P3 既有信任/权限规则；对方显示发送方、**文件数量与总大小**后明确接收。
3. 接收目录经授权后，对每个文件验证合法名称、目标、空间/冲突和 SHA256；先写隔离临时文件，成功后**非覆盖式提交**。文件的来源和系统 Copy/回收语义不改变。
4. 单文件按单任务展示；多文件批次归入统一任务中心的**一个批次任务**，可展开单项状态、总数量、已成功/失败/取消数量和错误原因；用户能够取消，断线不能把部分文件标为成功。
5. 传输完成，可打开接收位置或按原规则**主动**加入指定文件架；不能自动将任何接收物导入其他架或改变来源文件。

## 3. 分阶段真实验收要求

- **单文件**：中文/英文名称、同名冲突不覆盖、空/大文件、源/目标 SHA256、拒收/取消/断线/磁盘空间不足及断开后的临时文件处理。
- **多文件批次**：1 / 2 / 多文件数量、总大小统计；逐文件状态、一项失败但其余成功、整批取消、终态不会谎报全成功；多选和 UI 不重复发送。
- **安全边界**：文件夹输入明确拒绝并给可理解提示，不悄悄递归、扁平化、静默上传；符号链接/特殊路径、非法文件名、来源保护、目录权限、大小及任务并发受到约束。
- **真实互通**：首先对照官方 LocalSend ↔ 柠猫，再测试柠猫 ↔ 柠猫，两台 Windows 的真实网络身份、内容一致性及失败路径；loopback/模拟只能标记合成测试。
- **前台轻量**：不在双眼球/小架永久增加发送图标；发起入口跟随所选素材，设备与任务管理只在管理中心；不引入新付费服务或自动网络后台。

## 4. 后续单独阶段：目录递归传输

不属于当前 P3 首版验收阻塞项。未来提案需另外核查：

- 递归层级、相对路径与空目录保留、同名文件/目录多层冲突；
- Windows 长路径、保留名、大小写、非法字符、重解析点/符号链接与循环；
- 相对路径不逃逸到授权接收根目录、拒绝覆盖、原子/可恢复批次提交；
- 目录中断后的哪些文件可继续、权限回收与报告一致性；
- 与 P2 真实目录绑定/复制、文件架身份、失效引用及 SQLite 的兼容性。

未经过新的技术/安全 Gate，不得为了增加“发送文件夹”入口顺带修改 P2 的真实目录 Copy 语义。

## 5. 授权和工程约束不变

**先完整收束 P2 → 后 P3 最小 LAN 真机 → 再 P4。** 首次 LAN 监听/广播、配对、接收目录、防火墙更改，依然必须依据当次环境单独授权。不得动私人真实文件、用户数据库、公共 Release、网络/模型/付费账户；本项只是 GitHub 决策和设计记录。
