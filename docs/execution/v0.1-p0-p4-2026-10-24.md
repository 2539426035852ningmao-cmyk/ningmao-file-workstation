# 四、P0：先打通可靠的 Windows 文件基础

## 核心目标

**形成第一套真实可运行、可以完成文件收集和流转的 Windows 工作站。**

不要继续无限增加列表小功能。

优先从现有功能候选完成完整验证和必要修复。

### 必须打通的核心链路

资源管理器文件

↓

拖入柠猫文件架

↓

建立引用或复制到绑定目录

↓

查看缩略图、预览、选择与整理

↓

拖出到桌面、资源管理器或支持的创作软件

↓

安全保留来源文件

↓

关闭程序并重新启动

↓

正确恢复文件架与素材记录

### P0 必须实现或验证

1. Windows 原生应用可以独立启动。
2. 从资源管理器拖入真实文件。
3. 临时文件架默认只保存引用。
4. 绑定目录默认复制并保留原文件。
5. 同名文件不静默覆盖。
6. 文件夹、路径和中文文件名正确处理。
7. 图片缩略图正确显示。
8. 单击选择、空格预览、双击默认程序打开。
9. 文件架内部手动排序。
10. 将文件拖出到 Windows 目标位置时明确保证安全 Copy 语义。
11. 复制进度、取消及失败提示。
12. SQLite 状态持久化和重新启动恢复。
13. 失效引用可以保留并手动重新定位。
14. 退出、异常退出、路径失效和复制失败时保护原始文件。
15. 完成真实 Windows 构建与一次集中验收。

### 最高优先级技术问题

必须重点解决：

**文件卡片直接拖出、内部排序与 Windows 原生拖入之间的冲突。**

研究成熟 Windows 文件拖拽实现。

可复用已有 drag-rs 等经验证组件。

不得把浏览器内部 HTML 拖拽当作 Windows 系统拖拽。

不得为了让拖拽看起来成功而偷偷移动原文件。

如果直接拖出能力仍存在技术限制，可以暂时保留安全的“拖出复制”按钮作为明确降级方案，但必须记录其限制，并把真正的直接拖出列为下一项核心攻关任务。

### P0 交付要求

交付：

- 一个可独立运行的 Windows 样机
- 对应的完整源码提交
- 自动测试结果
- 精确 EXE / MSI 构建标识
- 清晰的文件安全说明
- 一份真实 Windows 实机验收清单
- 已知问题与回滚方法

自动测试可以先完成，但真实原生验收不能用 CI 代替。

**不要因为尚未安排人工验收，就停止一切可安全并行推进的工作；同时也不能把未验收结果写成已经通过。**

# 五、P1：完成真正轻量、专业的小悬浮文件架

## 核心目标

将软件从大型文件管理界面调整为：

**小窗口、轻量、随用随开、文件内容优先。**

这是产品日常使用的主形态。

### 以 design.md 为设计合同

重点采用：

- 同心圆嵌套圆角
- 4px 基础间距体系
- 统一深浅主题
- 蓝色强调色
- 简洁的 Lucide 图标
- 系统中文字体
- 短文字、少注释、少解释
- 尽量少的常驻分隔线和工具栏
- 减少无效层级与重复操作

### 窗口方案

以已经做过的紧凑候选为起点：

- 默认建议 420×520
- 最小建议 340×320
- 可手动调整与记忆尺寸
- 超出小窗复杂度的功能进入管理中心

这些数值是待用户实机验收的建议，不是未经批准就永久固定的规格。

注意检查当前 Tauri 正式窗口参数是否仍采用旧的大窗口配置。

不能只在测试预览里实现小窗口，正式应用却一直以 1000×720 打开。

### 小窗口只保留核心结构

顶部：

- 当前文件架
- 文件架切换
- 搜索
- 添加
- 更多菜单

中部：

- 文件缩略图 / 列表
- 文件名
- 极简状态
- 直接拖入拖出区域

按需出现：

- 选中操作
- 详情抽屉
- 排序
- 筛选
- 任务进度
- 错误提示
- 网络发送入口
- 未来 AI 操作入口

禁止：

- 默认固定左侧导航栏
- 默认展开右侧 Inspector
- 堆叠品牌标题和文件架大标题
- 同一功能出现多个重复按钮
- 大量解释性文案
- 为尚未完成的网络和 AI 功能永久预留大面积空 UI

### 保留当前已经开发的功能

现有网格、列表、缩略图大小、手动排序、时间排序、类型排序、大小排序、筛选和视图记忆应继续保留。

但低频操作统一放到更多菜单或按需面板。

**减少界面复杂度，不等于删除功能。**

### P1 交付要求

交付可运行紧凑窗口，至少验证：

- 三种代表性尺寸
- 深浅主题
- 键盘操作与焦点
- 文件名溢出
- 缩略图与文字显示
- 拖入拖出时的视觉反馈
- 文件选择与内部排序
- 窗口放大缩小时布局不跳动
- Windows 125% / 150% 缩放下的实际表现

输出截图与可运行候选供用户一次集中判断。

不要连续多轮打磨微小像素细节。

先达到统一、美观、稳定、顺手的基线，再进入 P2。

# 七、P3：打通网络文件传递

## 核心目标

从仅在本机整理文件，扩展为真正可在设备之间传递文件。

优先实现最短、最可靠的局域网传输闭环。

### P3 第一阶段：LAN 局域网

实现：

1. 两台受支持设备能够在同一局域网中发现或手动连接。
2. 用户主动选择接收设备。
3. 选择文件或文件夹发送。
4. 接收设备明确确认接收。
5. 通过受保护的连接传输实际文件字节。
6. 显示传输速度、进度、结果和错误。
7. 网络中断时能准确提示失败。
8. 重名目标不自动覆盖。
9. 收到文件后可直接加入文件架。
10. 传输结果进入统一任务记录。

优先研究成熟开源方案，例如 LocalSend 及其协议或可复用实现。

但必须先核查其真实协议能力、许可证兼容、维护状态和 Windows 集成代价。

**优先复用成熟传输协议及组件，不从零设计不必要的加密协议。**

如果已有方案集成成本较高，可先做经过验证的最小点对点传输适配，不无限期研究。

### P3 第二阶段：不同网络传递

在局域网稳定后，再设计：

- 异地设备连接
- 可信设备身份
- 用户授权
- 端到端加密或等效安全机制
- 离线状态
- 文件冲突处理
- 可恢复传输
- 必要时的中继方案

跨网络能力不得未经安全审核就对公网开放本地文件目录。

### P3 第三阶段：同步与共享

后续按需支持：

- 指定文件夹共享
- 设备之间的引用和文件访问
- 可选同步
- 离线重新连接
- 明确的双向冲突规则

同步属于更高风险能力，不要和首次局域网发送同时大规模开发。

### P3 交付要求

至少完成一次真实双端传输：

设备 A 选中真实文件

↓

点击发送

↓

设备 B 确认

↓

完成传输

↓

校验内容一致

↓

加入 B 端文件架

这是 P3 最重要的验收链路。

# 八、P4：AI 文件检索、分析和受控修改

## 核心目标

让工作站不仅能够存储与流转素材，还能帮助用户理解、检索、分类和整理文件。

### 先建立统一资源身份

为未来能力定义稳定边界：

- FileReference
- AssetIdentity
- FileProvider
- TransferProvider
- CommandRegistry
- JobQueue / EventBus
- SearchIndexer
- AiProvider
- PermissionBroker

这些名称是接口方向，允许根据现有代码调整，禁止为了名称统一而大规模重写底层。

### P4 第一阶段：本地检索

先实现真实的本地文件元数据索引。

支持：

- 文件名
- 类型
- 修改时间
- 大小
- 标签
- 文件架
- 已授权目录范围

在现有搜索能力基础上扩展跨文件架搜索。

索引不能默认扫描全部磁盘。

### P4 第二阶段：可选 AI 分析

通过 AiProvider 接入可用模型。

首批优先提供：

- 图片内容分析
- 文件名称建议
- 标签建议
- 文件分类建议
- 语义搜索能力
- 选中文件的简要信息整理

Google AI Pro / ChatGPT 订阅不能直接假定等于可供应用调用的免费 API。

使用任何云端模型前必须明确授权渠道、数据上传范围和计费方式。

**默认不新增付费 API。**

可以优先使用经过许可的本地模型、现有合法接入渠道或用户主动配置的提供器。

暂时没有可用 AI 提供器时，应保留正常文件检索功能，并明确提示 AI 尚不可用；不能用固定模拟文本冒充真实 AI 分析。

### P4 第三阶段：AI 建议与修改

AI 可以提出：

- 批量重命名建议
- 标签与分类建议
- 文件整理建议
- 重复素材识别建议

但真正修改文件前必须：

1. 展示修改前后差异。
2. 明确用户授权范围。
3. 提供取消选项。
4. 防止重名覆盖与路径失效。
5. 记录操作结果。
6. 支持可实现的撤销或恢复。
7. 发生错误时保护原始数据。

AI 不允许默认静默删除、覆盖、移动或上传用户文件。

### P4 最小完整闭环

用户选择一组文件

↓

AI 或本地检索找到目标

↓

分析并提出标签 / 重命名建议

↓

用户预览和确认

↓

执行受控修改

↓

结果记录并可追溯

- 任务恢复
- 网络权限
- AI 文件修改风险

Gemini 是独立审查助手，不是第二个可以随意修改主仓库的开发者。

# 十、加速开发的工作制度

这是本轮最重要的执行变化。

## 10.1 从“零散功能驱动”改为“完整结果驱动”

不要再以：

“又增加了一个按钮”

“又增加了一种排序”

“又补充了一个筛选条件”

作为主要进度成果。

以后优先汇报：

- P0 的文件流转链路是否真实打通
- P1 的紧凑文件架是否完整可用
- P2 的悬浮球与 Dock 是否真实运行
- P3 的双设备传输是否成功
- P4 的 AI 辅助整理是否完成真实闭环

细节问题应该合并到对应阶段的回归任务中处理。

## 10.2 采用最小完整闭环

每一阶段优先交付可运行的端到端版本。

先实现最重要的 20% 能力，打通实际操作路径，再完善其余复杂能力。

但以下要求不能简化：

- 数据安全
- 身份与权限
- 关键错误处理
- 用户授权
- 真实操作验收
- 可恢复和可回滚

不要把“快速开发”理解为跳过这些要求。

## 10.3 控制研究和原型数量

已有技术框架和设计系统不再重新比较。

优先寻找可以直接复用的成熟开源实现。

仅当当前技术路线确实无法实现关键功能时，才允许开展局部技术试验。

研究必须有明确结论：

- 能否使用
- 集成成本
- 许可证
- 风险
- 采用还是放弃

不要长期停留在研究报告和多版本 UI 比较。

## 10.4 使用云端与本地混合开发

优先在后台或云端完成：

- 构建
- 单元测试
- 静态分析
- GitHub CI
- 合成数据浏览器测试
- 源码审查
- 安装包完整性检查

只有真实 Windows 原生交互时才启动：

- Tauri 桌面窗口
- 资源管理器
- 系统拖拽
- 安装程序
- 多显示器检查

未经用户明确允许，不擅自打断用户正在进行的桌面工作。

## 10.5 集中安排验收

不要每修一个细小功能就让用户重新安装、截图、反复测试。

把同一阶段的必要原生项目整理成**一份集中验收清单**。

例如 P0/P1 一次验收覆盖：

- 启动
- 小窗口
- 文件拖入
- 复制
- 拖出
- 预览
- 文件架切换
- 关闭和重启
- 异常提示

验收前先准备合成素材、隔离数据环境和回滚方式。

未经用户授权不要执行安装、升级、卸载或窗口自动化。

## 10.6 自动连续推进

对于已确定的产品需求和低风险工程任务，你可以自主推进，不需要每一步等待用户答复。

但以下事项必须暂停请求确认：

1. 高风险真实文件操作。
2. 文件批量删除或覆盖。
3. 重大架构替换。
4. 新增收费服务。
5. 开启网络对外访问。
6. 启用涉及隐私的云端 AI 处理。
7. 正式 UI 视觉方向变更。
8. 不可逆的数据库迁移。
9. 发布正式安装包。
10. 需要真实用户桌面验收或额外系统权限的行为。

遇到这些关卡时，一次只向用户提出一个必要问题，并给出推荐方案。

不要为了其他低风险工作也反复询问。

# 十一、阶段质量门槛

- 对应构建产物
- 测试报告
- 已知限制

- 用户验收状态
