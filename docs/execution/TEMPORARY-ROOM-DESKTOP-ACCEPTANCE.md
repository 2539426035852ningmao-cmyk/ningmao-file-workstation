# 临时互传区 Windows 接入

自托管网页生成的同一邀请可在工作站「文件互传」下的「临时互传区」使用。填入链接和显示名称后加入，需要审批时由群主在网页确认；申请获批后点击刷新。发送端选择单个文件，由本机授权读取，接收端选择绑定目录并通过 Windows 原生确认框后校验落盘。

站点会话按来源保存在工作区的 Windows DPAPI 保护文件内。客户端使用系统 TLS 验证及固定 API 路径，拒绝重定向。准备文件的哈希用于检测源变化。同一次上传沿用任务编号，重复提交复用站点已经确认的文件记录。撤回后旧编号不能重新发布。有明确结果后，主动再发会获得新编号。接收结果按文件、站点和目录在 WebView 配置内留存，未确认的任务先到目标架核对。

## 验收

- 浏览器界面测试使用合成 IPC 验证发送使用所选文件、未选绑定目录时不能点保存，以及刷新不重复请求已保存项。旧互传界面专项 18 项通过。
- 自托管站点 API 回归验证同一次上传重试返回同一 ID，撤回后重试返回 410。网页双向落盘回归通过。
- 本机 Windows 原生 EXE 与实际 Chromium 连接同一回环 HTTP 站点。测试通过实际 WebView2/Tauri IPC 加入同一房间，浏览器上传后经 Windows 确认框保存，旧同名文件内容未变化，副本为 `received (1).txt`。原生发回时同一编号请求两次，站点返回同一 ID；Chromium 下载并独立核对源哈希。
- 从浏览器到 Windows 的落盘 SHA-256 为 `4a8d07c0a9bc811b6fe173e2834cad250aa7156a0bd4371a16ba7eadeeadc28b`。Windows 到浏览器为 `689a2775a219f9b325dcabedc140c747430d71e8cdf6af1744afa78507e09f3b`。仅用独立合成 Store、目录和 WebView 配置。
- 本机 Rust 邀请校验、Clippy、桌面构建通过。原生测试首次发现 reqwest 缺少 Rustls 提供者，初始化后复测通过。首次 UI 探针超时由原生收件确认框等待交互引起，点击实际确认按钮后落盘。

独立客体单独验收 MSI 安装和 Windows ↔ Windows。前次用于 Chromium 的 QEMU 客体首启桌面设置未完成。此记录的原生 EXE 实测在宿主 Windows 完成。
