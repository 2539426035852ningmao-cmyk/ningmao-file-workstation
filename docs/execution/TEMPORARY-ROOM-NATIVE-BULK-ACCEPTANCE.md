# Windows 原生分块互传验收

此候选接续网页分块互传 PR #108。站点开启磁盘分块暂存时，Windows 可以从所选文件架发送一个最高 20 GB 的文件，也能保存网页或另一台 Windows 发来的分块文件。上传前本机流式计算 SHA-256，读取站点回执后从确认偏移继续。接收前点选真实绑定目录，由 Windows 原生对话框确认。接收端每次读取 4 MiB，遇到一次中断从当前范围再请求一次，接收完成并校验后才使用原有同名编号规则落盘。网页入口已有的供件切换继续由网页负责。

上传失败后，重新点击同一文件的发送按钮即可查询站点已确认的偏移。下载再次失败时清理暂存，重新接收从头开始。界面显示来源校验、上传或下载进度。站点未开启分块时桌面入口仍走原有 64 MiB 路径。

## 实测

桌面端可在「更多操作 → 文件互传 → 临时互传区 → 发起临时互传区」连接已运行的自托管站点。填写显示名称和站点地址即可建区，默认需要群主或管理员批准加入。房主可以复制邀请链接、单独保存管理恢复码。访客申请后，房主点击「刷新互传区」，再选择「批准」或「拒绝」。建区后从同一个面板发送文件或选择绑定目录接收。

2026-11-21 的原生回环复测使用 Windows 调试 EXE，SHA-256 为 `641b1403ac9ea9459dffb6e699e1817a7b69994128b3117070140884a52dfce2`。新房间在 Windows 建立，独立访客在待审批期间读取返回 403。Windows 批准后，访客从该房间下载了群主发出的合成文件，字节与源文件一致。Windows 加入同站的另一房间后，原房间的群主权限仍有效。桌面界面回归另外确认了创建、复制邀请和审批入口。

在隔离 Windows 工作区用原生 EXE 实传 80,000,000 字节。对第二块分别注入一次上传与下载断开。重新发送复用任务编号，从 4,194,304 字节续传。接收通过 Windows 原生确认框，下载自动重试同一范围，保留目标原件并保存为 fixture (1).bin。落盘后重读的 SHA-256 为 b5a51e6313f77706992b93120c694c2c1a5b99159839ff7241e4cb1018b55e10。

先构建桌面 EXE。在 apps/web 运行 node tests/native-bulk-room.mjs EXE STATION_DIRECTORY WORKSPACE_DIRECTORY [BYTES]。默认使用 80,000,000 字节，20 GB 验证建议站点与工作区使用不同卷，每卷准备至少 41 GB 可用空间。测试只操作自己创建的合成目录，结束后清理。桌面构建、严格 Clippy 和五项桌面界面专项已通过。随后已完成[两台 Windows 虚拟机的安装端互传](TEMPORARY-ROOM-WINDOWS-GUEST-ACCEPTANCE.md)。

## 下载中途撤回

2026-11-20，在 Windows 本机隔离工作区复测 80,000,000 字节。测试检查原生收件框的标题「确认接收文件」和不覆盖原文件的说明。普通断线仍从 4,194,304 字节重新请求，完整副本的 SHA-256 与源一致。

第二次接收同一合成文件时，群主在站点收到第二块请求时撤回。接收端收到撤回响应后停止分块请求，删除本次的部分暂存，废止收件票据，并将任务标为「中断」，清空已删除的暂存路径。目标目录里只保留测试预置的原文件和第一次完整保存的副本。复测命令同上。此场景覆盖下载过程中收到站点撤回响应的窗口。双虚拟机安装证据和真实局域网、跨网证据各自记录。
