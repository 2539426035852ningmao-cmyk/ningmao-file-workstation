# 二、立即实行新的自主开发授权制度

从本任务开始，你需要按照以下四级风险体系管理开发和验收。

## R0：极低风险

例如：

- 文档文字修正
- 无行为变化的注释精简
- 无意义重复文字清理
- 文档索引与状态更新
- 已有测试说明完善
- 不改变接口行为的简单格式调整
- 安全且不改变运行语义的测试辅助改进

### 授权

允许直接自主处理。

可以自主完成：

分析 → 修改 → 检查 → 自主验收 → PR → 合规合并。

符合仓库规则时无需逐项请求用户批准。

对于此类改动，不需要人为制造复杂审查流程；但仍必须遵守现有 GitHub 主分支保护和必要检查。

## R1：低风险

例如：

- 纯视觉层的小型样式修复
- 小组件对齐
- 圆角和间距统一
- 图标一致性
- 非关键文字调整
- 已有菜单的非破坏性布局优化
- 不改变文件操作的显示问题
- 已有功能的低风险可访问性修正
- 不改变持久化格式的前端交互小修复

### 授权

允许自主开发、自主 Code Review、自主测试、自主验收。

在满足下列条件时，可免除用户逐项审核：

1. 不修改文件安全语义。
2. 不改变 SQLite schema 或数据迁移。
3. 不扩大系统权限。
4. 不增加外部网络访问。
5. 不影响真实文件复制、移动和删除。
6. 相关自动测试通过。
7. 没有新的严重错误。
8. 可以通过普通 Git revert 回滚。
9. 没有改变已批准的核心视觉方向。
10. 符合 GitHub PR 与保护规则。

满足条件后，允许自行完成常规 PR 合并；如果平台要求独立审查者批准，必须遵守，不能伪造审查或绕过保护。

## R2：中低风险

例如：

- 当前文件架的显示状态优化
- 已有筛选和排序的局部缺陷
- 非破坏性的操作反馈优化
- 搜索面板的小型交互修复
- 管理中心已有只读视图优化
- 不改变数据格式的任务状态显示修复
- 已有键盘快捷操作的安全范围内调整
- 不涉及真实文件写入的性能优化

### 授权

允许自主完成设计分析、代码开发、专项测试和技术验收。

可以免除用户对每项小功能的手动体验审核，但必须有客观验收证据。

附加要求：

- 明确改动范围。
- 添加或执行针对性回归。
- 检查是否影响上下游组件。
- 保留修改前后行为对比。
- 失败时可以快速回滚。
- 在 PR 中记录自主验收结论。

对于完全局部、没有权限、文件写入、数据迁移或跨窗口所有权变更的改动，符合上述要求并经仓库允许，可以按普通流程自主合并。

**凡是影响原生窗口生命周期、文件拖放、引用归属、任务取消、数据库状态或用户素材的改动，即使代码很少，也自动升级为 R3，不得自定为 R2。**

## R3：高风险和重大决策

包括：

- 删除、覆盖或移动真实文件
- 修改文件复制或拖出 Copy 语义
- 修改持久化格式且涉及不可逆迁移
- 大规模数据处理与批量真实文件重命名
- 修改安全权限模型
- 开放公网或局域网文件访问权限
- 引入网络监听与新设备信任关系
- 上传私人素材到 AI 服务
- 新增付费服务或 API
- 修改重大架构
- 替换主要 UI 设计系统
- 改变正式产品视觉方向
- 发布正式安装包
- 升级、卸载或清理用户已有安装
- 修改受保护主分支规则
- 合并尚未获得产品安全验收的关键阶段 PR

### 授权

可以自主研究、实现隔离原型、编写测试、提交 Draft PR 和准备证据。

**但高风险操作、实际启用、正式合并或正式发布必须取得用户相应批准。**

不得把“用户允许加速开发”解释为允许绕过这些安全门槛。

# 三、减少无意义审核的具体要求

今后不再出现下面这种工作方式：

完成一个小按钮 → 提问 → 等待用户 → 完成一个小菜单 → 再提问 → 等待用户。

请改为：

**集中识别问题 → 一次实现相关修复 → 完整自动回归 → 自主审查 → 阶段交付。**

将同一模块的低风险问题尽可能合并到同一个功能 PR。

小范围修复可以自主验收。

用户只需要在以下时机参与：

1. 整体样机的真实操作感验收。
2. 影响用户数据安全的操作确认。
3. 重大设计方向变化。
4. 新网络或隐私权限启用。
5. 付费授权。
6. 正式发布和不可逆变更。

不要为了等用户回复而停止其他独立、安全且可以继续的工作。

每次确实需要用户决定时，只问一个问题，并提供推荐选项。

# 四、第一阶段：立即进行 P2 r13 集中 Windows 实机验收

## 这是当前最高优先级

先不要继续开发大量新的筛选、按钮、页面和效果动画。

我们需要证明 r13 已经从代码变成真正可用的 Windows 桌面软件。

### 4.1 自动准备验收环境

你负责：

- 确认当前最新 P2 功能版本。
- 定位对应精确 EXE 和 MSI 产物。
- 校验 SHA256 与构建来源。
- 使用专门的合成测试文件。
- 准备隔离的测试数据目录。
- 不读取或扫描用户私人文件。
- 保留历史 r10–r13 候选。
- 准备原始文件哈希与恢复手段。
- 优先使用 EXE 进行验证，不自动安装 MSI。
- 准备一次性可执行的验收清单。

以上可在后台完成。

### 4.2 真实桌面验证

在需要打开应用和操作 Windows 桌面时，先向用户申请一次明确的集中验收授权。

获得授权后，尽可能一次完成以下操作：

**场景 A：悬浮球与小窗口**

- 启动真实程序。
- 检查默认小窗口尺寸。
- 收起成为悬浮球。
- 单击展开。
- 拖动位置。
- 再次收起。
- 关闭窗口并从托盘恢复。

**场景 B：文件架拆分与合并**

- 创建多个文件架。
- 将其中一个拆分为独立窗口。
- 同时移动两个窗口。
- 在不同文件架中整理文件。
- 将独立窗口合并回主窗口。
- 确认素材、标签与排序没有丢失。

**场景 C：Dock 与贴边**

- 将多个文件架收起。
- 检查 Dock 是否正确收纳。
- 拖动悬浮入口。
- 将文件靠近入口。
- 检查安全展开。
- 将文件放入正确目标架。
- 取消一次拖入。
- 检查没有重复导入和错误目标。

**场景 D：文件安全回归**

- 从 Windows 资源管理器拖入合成文件。
- Ctrl / Shift / 框选多个文件。
- 将选中文件拖出到资源管理器。
- 检查来源是否保留。
- 检查目标内容哈希。
- 测试绑定文件夹安全复制。
- 测试重名自动编号。
- 检查内部排序。
- 测试预览、默认打开和引用状态。

**场景 E：管理中心**

- 按需打开。
- 浏览真实索引记录。
- 搜索和筛选素材。
- 编辑已有测试标签。
- 核查批量标签操作。
- 关闭后回到悬浮文件架。
- 确认不会产生重复窗口或数据错误。

**场景 F：重启恢复**

- 调整各窗口位置及尺寸。
- 收起部分文件架。
- 完整退出软件。
- 重新启动。
- 检查多个架的身份、布局和数据。
- 检查旧布局文件未被错误覆盖。

### 4.3 验收分类

每项结果严格分为：

- PASS：实际执行并通过
- FAIL：实际执行并失败
- BLOCKED：环境或权限阻碍
- NOT TESTED：尚未执行

不要将自动测试、浏览器模拟与真实 Windows 原生验收混为一谈。

出现问题时：

- R0/R1/R2 问题可以自主修复并回归。
- R3 问题建立高风险记录，优先制作修复候选，但相关操作及合并仍遵守用户授权。
- 不因个别非关键视觉问题阻塞全部 P2 技术开发。
- 不因文件损坏、目标误判、丢失引用等重大风险继续扩大真实文件测试。

### 4.4 P2 首轮验收后立即做什么

形成一份统一结果报告：

- 真实可用的功能
- 当前阻碍
- 用户反馈
- 高优先级修复
- 可自主处理的小问题
- 尚未验证的 Windows 环境
- 精确源码与构建版本
- 回滚方案

对于无需重大决策的修复，直接进入开发和回归，不要反复要求用户确认。

# 六、第三阶段：加速进入 P3 网络文件传递

P2 核心能力经过实机验证之后，尽快建立 P3 的独立开发分支。

## P3 第一版只做一个真正的网络闭环

**Windows 设备 A → Windows 设备 B。**

步骤：

1. 用户主动发现或添加另一台设备。
2. 通过明确的确认建立信任。
3. 从文件架选中文件。
4. 点击发送。
5. 对端确认接收。
6. 实际传输文件。
7. 显示进度。
8. 接收完成后校验 SHA256。
9. 保留来源。
10. 自动提供加入接收端文件架的操作。

先让这条链路真实可用。

不要第一天就同时开发：

- 公网中继
- 云存储市场
- 自动同步
- 多账号管理
- 大型设备控制台
- 多端复杂权限体系

### 技术原则

优先研究 LocalSend 等成熟开源方案。

尽量复用已经验证的传输协议、加密与网络组件。

文件传输必须通过新的受限服务边界连接现有 FileReference、任务队列和权限控制。

网络层不能直接绕开 Rust 文件安全逻辑。

首次开放局域网发现、监听端口、配对及真实设备接收前，需要集中申请一次用户授权。

后续经批准的局部 UI、日志、进度显示和失败提示可按 R1/R2 自主开发。

### P3 交付门槛

必须有一次真实双设备文件传输证据。

不能以本机模拟收发代替。

完成 LAN 后再进入跨网络传输和可选同步。

# 七、第四阶段：继续推进 P4 AI 与插件

P4 不要从复杂的 AI 平台开始。

优先形成：

**真实文件 → 搜索或分析 → 生成建议 → 用户确认 → 安全操作。**

### 第一阶段：本地元数据检索

基于现有 SQLite 及已授权文件架：

- 跨架搜索
- 名称、类型、大小、时间
- 标签与来源
- 失效引用
- 搜索结果快速定位

这一阶段不依赖外部 AI。

### 第二阶段：可选 AI 能力

定义可替换 AI Provider。

可以准备：

- 图片内容分析
- 自动标签建议
- 文件分类建议
- 智能命名建议
- 语义搜索
- 重复素材辅助判断

但不得将个人 ChatGPT Plus 或 Google AI Pro 订阅直接当作可免费调用的 API。

无合法可用提供器时，先完成本地检索和可选模型接入契约，不模拟成功的 AI 分析。

### 第三阶段：受控 AI 操作

实现：

AI 生成建议 → 展示差异 → 用户确认 → 执行 → 记录与恢复。

所有真实文件改名、移动、覆盖或外传均遵守 R3。

### 插件与接口

为未来扩展保留：

- FileProvider
- TransferProvider
- CommandRegistry
- JobQueue
- PermissionBroker
- AiProvider

但只在具体功能真正需要时逐步实现。

不要为未来不确定的插件生态提前建立庞大框架。

# 八、让开发真正加速的规则

## 8.1 阶段成果优先

以后不要主要汇报：

“新增了三个按钮”

“优化了四个图标”

“增加了一项排序”

请主要汇报：

“P2 的悬浮桌面闭环已经真实可用”

“P3 已完成两台设备之间的真实传输”

“P4 已完成实际素材分析和受控重命名闭环”

## 8.2 批量修复

同一模块多个 R0/R1/R2 问题集中修复。

不要为每个小问题建立一条独立的长流程。

## 8.3 阶段性 PR

以完整能力组织阶段 PR。

正常低风险维护可以自行合并。

需要人工安全验收的阶段代码继续保留受保护的合并关卡。

PR 数量尽量少，但不能使高风险修改和低风险修改无法分别审核。

## 8.4 减少重复测试

对未变动的模块不做无意义的手工重复验收。

根据依赖关系运行必要回归，并保留阶段完整测试。

但对不同精确二进制，不允许将旧版本原生结果冒充新版本通过。

## 8.5 不追求无止境的完美

满足功能完整、安全边界、基本稳定性和真实体验后，进入下一个阶段。

次要视觉问题、非阻断型细节可以进入统一优化列表。

不能为了一个微小的阴影、圆角或间距反复停滞开发。

## 8.6 低风险自动通过的真实含义

低风险自主验收意味着：

- Codex 可以按照规则判断技术通过
- 可以不要求用户逐项操作
- 可以按仓库正式规则合并允许自主合并的普通 PR

**不意味着可以绕过 GitHub 必需审查、关闭失败检查、跳过真实安全测试或伪造人工验收。**

## 8.7 持续推进与任务交接

可以自主推进已授权范围内的普通开发。

每个阶段必须留有 GitHub 记录和最新交接状态。

如果当前 Codex 会话即将结束，完成已有可执行工作后提交状态与下一动作，确保新会话能够直接接手。

如果没有真正建立定时或持续任务执行环境，不要声称仍在后台自动工作。
