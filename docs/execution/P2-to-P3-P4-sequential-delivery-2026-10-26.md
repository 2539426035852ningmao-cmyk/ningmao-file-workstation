- 43 项 V0.1 冻结需求 + P2 已确认 UI-B01–B07 + P3 免费轻量设计合同 + P4 44 项确认需求同时有效。发现冲突时先写 ADR/风险与最小方案，不静默修改业务规则。

- 采用已有设计系统、图标与深浅主题；真实交互优先于静态截图。选中上下文“一个功能一个主入口”，插件不能挤占小文件架。
- 保证默认无新增服务费：P3 首发 LAN 不用自建中央服务器；P4 基础搜索不用云端或下载模型。会员订阅不能假定为 API 授权。

## 3. P3：P2 通过后的第一条正式实现主线（无新增柠猫服务器费）

参照 [P3 免费/轻量合同](../design/P3-free-first-lean-ux-contract-2026-10-26.md)和 [Gate 0–2](P3-P4-implementation-gates-2026-10-26.md)。

- **P3-0 · 选型和隔离编译**：固定 LocalSend protocol/core 版本、上游 commit 和许可证，试验最小特性依赖与包体增量，不直接污染主 Cargo.lock；不合适则改用薄协议适配并记录 ADR。
- **P3-1 · 安全 loopback**：隔离双进程/合成文件验证会话、路径穿越和保留名拒绝、冲突不覆盖、哈希 SHA256、取消/断线/空间不足与临时文件清理。此处结果只能叫本机受控测试，绝不叫双机互通。
- **P3-2 · 真实局域网**：在用户明确批准首次 LAN 监听/配对/接收目录/防火墙后，跑官方 LocalSend ↔ 柠猫，再柠猫 ↔ 柠猫双 Windows 互传。默认手动接收确认，设备发现不等于设备信任，身份需验证。
- **P3-3 · 完整 UI + 任务中心**：选中文件 → 一处“发送到设备” → 选择可信设备 → 接收确认 → 受限临时目录加密流式传输 → SHA256 成功后不覆盖提交 → 可加入文件架。常驻待机不监听/扫盘，失败有清楚可恢复状态；管理中心唯一设备管理入口。
- **P3 放行**：真实双端加密/身份、安全路径、同名、取消/断线、源/目标 hash 对照、文件架引用、低资源占用和旧功能回归均有真机可复现证据。异地 NAT、公共中继、目录同步/云存储属于后续实验，绝非首版验收阻塞项。

### 已确认 D-02：P3 首版只做单文件与多文件批量

2026-10-26 用户选择 A：P3 **首版不支持整个文件夹/子目录的递归发送**。实现和真机验收必须覆盖单文件、多文件批次、逐项结果、拒收/取消/断线/同名不覆盖与 SHA256；目录、层级结构保留、符号链接及深路径递归是后续独立安全 Gate。遇到文件夹输入明确提示不支持，绝不偷偷自动遍历或扁平化发送。详细依据：[D-02 产品合同](../product/D02-p3-file-batch-first-scope-2026-10-26.md)。不可借此绕过 P2 原生关卡与首次网络监听专项许可。

## 4. P4：分四段交付，不把 44 项一次性塞入一个 PR

全部产品语义见 [P4 44 项](../product/P4-confirmed-decisions-01-44-2026-10-26.md)；先沿用 [现有 P4 Gate 3–4](P3-P4-implementation-gates-2026-10-26.md)。

### P4-A · 本地搜索最小真实闭环

- 基于**现有 SQLite/已有文件记录**建立可重建索引；先比较当前查询与 FTS5 unicode61/trigram，中文短词提供可靠 fallback；无新增模型/云/全盘扫描。
- Ctrl+F 当前架、Ctrl+K 跨架搜索，名称/类型/标签/来源/状态过滤，搜索结果跳转正确真实引用/文件架；同一物理文件多架引用聚合，回收/离线/失效/撤销授权均一致。
- 文件监听增量、防抖、后台低优先级，索引坏掉可重建不损用户成果；Windows 真机用中英文和批量合成材料验证。任何 schema 升级单独走 R3 数据关卡。

### P4-B · 图片相似 + 按需智能分析

- 先安全、低资源的图像近似/重复检测，再可选嵌入/语义；免费本地优先、兼容模型复用、不自动下载、不自动云端 fallback。
- 模型下载大小/授权/内存/许可证实测后请求许可；模型关闭时全文检索照常运行。视频关键帧/文档正文/OCR/音频语义作为渐进能力，沿用统一结果/预览，不抢基础验收。
- 标签/虚拟名称/分类作为**候选**，确认后才记录内部数据；真实重命名/移动/删除始终专项确认。用户反馈是显式本地改排序，可删除/复位。
- 用户可控缓存、离线索引、隐私撤销、备份可重建；严禁默认发真实素材到第三方云端；网页会员不是付费 API 额度。

### P4-C · 可用的插件生命周期闭环

- 先做一个**无模型/无需网络的官方安全示范插件**：只读取用户授权元数据 → 提出标签建议 → 用户确认写内部标签。证明注册、安装、启用、停用、卸载、权限撤销、故障隔离和回滚。
- 原生与第三方插件必须由宿主的 PermissionBroker / CommandRegistry / JobQueue 等**概念接口**协调（具体实现复用现有代码），不能自行索取任意本地路径/扩权。权限按任务与范围授权，可记忆低风险范围，随时撤销，高风险独立批准。
- 已验证来源、官方、自行导入分级展示；包完整性/兼容性/权限变化检查，更新可回滚。插件卸载不删除已确认的柠猫内部标签及引用。
- 功能按素材上下文显现，重复能力合并成一个入口，用户默认提供器优先；其余按本地/免费/已授权/兼容排序。插件市场、复杂开发者门户、无验证的完整 OS 隔离承诺后置。

### P4-D · 安全工作流与资源调度

- 从用户手动触发的只读流程开始：识别 → 检索 → 生成整理建议 → 用户审核；由主程序只传递当前任务必要引用和结果，不跨插件继承权限。
- 用持久任务检查点、准确终态、防重复提交、失败单步重试、人工继续/取消与记录保全。真文件写入恢复前必须检查当前磁盘状态，不能盲目补偿/重放。
- 后台动态并发 CPU/RAM/GPU，优先用户正在使用的文件架和创作软件；自动化仅允许经特别配置的指定范围低风险步骤，付费/联网/真实写盘不能被默认自动化规则授权。
- P4 完成判据是**逐段能力真实工作并与 P2/P3 一起回归**，不是把所有未来模型/插件商店/跨设备功能一次完成。

## 5. GitHub 记录与 PR 推进流程（Codex 必须执行）

1. **单一真实来源**：P0/P1/P2 已有 Issues 和堆叠 PR 保留；P3/P4 跟踪沿用 [#37](https://github.com/2539426035852ningmao-cmyk/ningmao-file-workstation/issues/37)。新议题仅在独立闭环、确需追踪时创建；不要复制一堆无用 issue。
2. **每阶段工作分支 + PR**：研究/文档与正式运行时代码分开；P2 原有堆叠历史按基线合并；P3 LAN 单能力闭环、P4 搜索、AI、插件、工作流按安全性拆 PR；R3 schema/data/security 独立审查。
3. **变更说明**写清楚：功能前后对比、保护了什么、准确测试命令与结果、平台/版本、原生 vs 模拟区别、源码/产物 SHA、许可证、资源增量、已知 FAIL/PARTIAL/NOT_TESTED、回滚路径。
4. **自动化**：安全范围内由 Codex 自行核实、编码、跑测试、修正、推 PR、读 CI；CI 失败不得绕过。允许依既定规则推进 R0/R1 与符合条件的 R2；**R3/原生高风险/网络首次监听/付费/真实数据修改/正式发布**必须等待明确授权。
5. **阶段状态板**：每次推进时更新 issue/checklist/文档，只使用 `planned / implementing / verified-in-CI / verified-on-Windows / approved / merged` 等准确状态。P3/P4 调研通过并非真实产品 PASS。
6. **阶段交接**：P2 原生验收缺项和合并门槛未闭合，不改写 P3/P4 正式安全能力；能并行的仅是隔离研究/合成测试。P3 LAN 真机通过阶段关卡后，再将 P4 正式实现排入主线。
7. **统一回滚**：各能力可关闭/回滚到最后稳定版本，旧数据兼容第一优先。合并后对 main 跑全量集成；任何回退不得抹掉用户的 SQLite 或个人文件。
