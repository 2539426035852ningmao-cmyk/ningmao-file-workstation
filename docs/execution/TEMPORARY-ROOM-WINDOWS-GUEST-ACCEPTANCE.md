# 两台 Windows 虚拟机的安装版互传验收

2026-11-20，应用以 D15 接续分支的 `14584f6` 为源码。使用 QEMU 11.1.0 的 TCG 软件仿真，在两台 Windows 10 Enterprise LTSC 2021 客体的正常桌面运行工作站。微软评估 ISO 的 SHA-256 为 `e4ab2e3535be5748252a8d5d57539a6e59be8d6726345ee10e7afd2cb89fefb5`。[微软镜像校验表](https://download.microsoft.com/download/c/1/1/c11d2ca5-967c-45c0-bc7d-2d9ca3f1fe07/Windows10Enterprise22H2HashValues.pdf)

客体 A 从微软安装程序完成系统安装。客体 B 在测试开始前复制系统磁盘，使用独立虚拟磁盘、UUID、网卡 MAC 与机器名，并在自己的系统中卸载后重新安装同一 MSI。两台报告 Windows 10.0.19044 和 MSI 安装状态 0。每台用独立工作区、WebView2 配置、收件目录及房间成员身份。实验桌面带 Windows 评估许可证过期水印。

MSI 的 SHA-256 为 `a8ad4f63b806ea0db53eb437f341628e03768c89fd9ffb0ce748e51471cdab5e`。从 MSI 的 app.cab 提取 File 表中的主程序，与两台实际安装的 EXE 分别比对，SHA-256 均为 `63810041c62a90130db35192a2bca44caadbcd61148a0cc5728d7d86c349bf00`。包外 EXE 与内嵌 EXE 有三字节差异，位于 Tauri 的包类型标记，分别为 UNK 和 MSI。

## 复测顺序

1. 在两套独立 Windows 工作区安装同一预览 MSI。站点启用分块存储并采用信任链有效的 HTTPS。两台用同一邀请加入，独立选择绑定收件目录。
2. A 发送 4,194,577 字节的合成文件。测试站点在上传偏移 4,194,304 字节时关闭一次连接。以相同任务编号重试，站点从该偏移继续，重复请求仍只显示一个文件。
3. 关闭 A 后，B 先拒收再确认。测试站点在下载范围 `bytes=4194304-4194576` 时关闭一次连接，B 从同一范围重试。目标目录已有同名文件，落盘副本为 `native-a (1).txt`。旧文件内容保留，副本的重读 SHA-256 与 A 源文件一致，为 `daa66055a9d885e318dc4aa03d26dcd8b74d994c9eef9112e2ec9a1628bb4ce8`。
4. B 发回等大小的另一份合成文件并关闭。A 重启后重用原有房间身份，打开同一互传区确认后保存为 `native-b (1).txt`，原同名文件未改动。A 重读落盘文件的 SHA-256 为 `5f47293fce1644c6e4dfded10c67ef48ddaf22b1d427b828112a18ab2e5ad6b8`，与 B 源一致。站点记录两台各一个成员身份。

本次使用同一宿主上的两个 QEMU 客体及虚拟 NAT，两台交替运行，站点绑定宿主回环地址，并在两台切换期间持续提供暂存。原生对话框仍使用「网页传来」的旧文案，即使发送端是 Windows。这次双客体场景使用 4 MiB 加 273 字节的文件，20 GB 证据见[原生回环验收](TEMPORARY-ROOM-NATIVE-BULK-ACCEPTANCE.md)。局域网直传的独立复测见下文。

## 两台 Windows 虚拟机的原生局域网直传

同一对 Windows 10 客体同时运行。QEMU 的虚拟以太网卡通过绑定宿主回环的 socket 后端互联，无网桥、NAT 或外部网络。两台客体各使用独立磁盘快照、机器名、工作区和 IPv4 地址。测试应用使用普通权限。新版复测预先在客体快照中启用该 EXE 的 TCP 53317 和 UDP 53319 入站规则，只接受本次虚拟网段的流量。

旧 MSI 在两端完成 UDP 设备发现和 TLS 指纹核对，错误指纹被拒。两边先拒收，再确认重试。B 收到并校验了 A 的 4,194,577 字节文件，原同名文件保留。A 发送端显示传输结果未确认。隔离网段抓包显示，B 在 A 关闭上传连接后才尝试发回响应。用同一接收实现和合成文件在回环重现，在发布文件后的任务记录中注入 7 秒延迟，旧版回执等待超时，但落盘文件哈希正确。

应用修复提交 `93591b4`。上传完成后的回执等待由 5 秒调整为 30 秒。局域网连接建立、握手、等待接收方允许上传及取消的超时沿用原设置。回环回归检查模拟的延迟回执和实际落盘内容，旧代码在该用例超时，修复后通过。

2026-11-20，新版原生 EXE 的 SHA-256 为 `5fd976f3dab413f225c324371042f774b72442cd8a2528d145fbc3d01e63f98d`。两台使用同一 EXE 依次完成 A 发 B、B 发 A，各 4,194,577 字节。每个方向先拒收一次，再确认重试。两个发送端均取得完成回执，接收端均保存 `fixture (1).bin` 并保留各自的 `fixture.bin`，发送源文件哈希保持一致。A 重读收到的文件为 `daa66055a9d885e318dc4aa03d26dcd8b74d994c9eef9112e2ec9a1628bb4ce8`，B 为 `2a536056615f8cab0b4182fb367ed9aff1b04b72ff8de57b684228e860da5efc`。两台最终都主动关闭接收。此轮通过顺序双向收发验收。

复测脚本为 `apps/web/tests/native-lan-guest.cjs`。将两台客体分别命名为 `ningmao-lab-a`、`ningmao-lab-b`，在隔离的虚拟网段分别配置 `192.168.253.10/24`、`192.168.253.11/24`。在两个客体中用 Node.js 24 和仓库已用的 Playwright 运行 `node native-lan-guest.cjs ROLE EXE SHA256 [WEBVIEW_CACHE]`。`ROLE` 分别为 `a` 和 `b`。脚本给每次运行建立全新的合成工作区，通过本机 WebView2 调用真实应用命令。它检查默认未监听、设备指纹、收件决定、同名保留、两个方向的 SHA-256 和关闭接收。客体防火墙入站许可须在两端就绪，然后同时运行脚本。

### 多文件批次断链与重试

使用 `node native-lan-guest.cjs ROLE EXE SHA256 WEBVIEW_CACHE faults`。A 发送两项合成文件，B 依次确认接收。监听隔离 QEMU socket 后端的数据量，在 A 向 B 的 TCP 53317 发送约 512 KiB 后用监控口 `set_link e1000.0 off` 断开 A 的虚拟网卡。等待约 70 秒后用 `set_link e1000.0 on` 还原。脚本会核对 A 的中断状态、B 的失败终态及暂存清理，再验证主动取消和重试。成功时每台输出 `FAULT_SCENARIO_PASSED`，并依次核对原文件、同名编号文件和落盘 SHA-256。

修复提交 `00ab2dd`。采用同一接收实现的回环用例在第一个文件传到一半时结束发送端连接。接收端清掉部分文件后，旧实现仍保留后续待传项的占位，下一请求返回 409。修复会作废尚未启动的上传票据。已经在传的其他文件可正常收尾。回环复测验证新一轮能重新得到同意，旧票据返回 403，两项文件均可重新传送并落盘。并发任务状态用例验证一项仍在传时不会提前宣布批次结束。

2026-11-20，双客体使用修复后的原生 EXE，SHA-256 为 `ee2d91932c42a5a00790cc2a0ad5ec4ec5edab85b13cd087663dd933398196b6`。首次尝试未等到两端同时就绪，A 的 WebView2 调试入口超时，B 等待发现超时。第二次在同一隔离网段通过，双方脚本退出码均为 0。
