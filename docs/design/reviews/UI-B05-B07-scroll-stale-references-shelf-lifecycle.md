## 0. 核心设计原则

用户的核心诉求不是简单“再加删除功能”，而是：
- 静态界面减少常驻控件噪声；操作意图出现时控件才及时显现。
- 文件移动/删除后，其**引用卡片不能永久不可清理**；能更新、重新连接、移除和恢复。
- 自己创建的文件架**能直接在切换菜单本行管理/移入回收站**，**无需右键、无需打开第二层管理页面**。
- 与既有的**来源文件保护、文件架独立身份、多窗口/Dock 和原生文件 DragSession**严格兼容。
- 本轮仅确认产品问题和无额外层级的总体意图；视觉参数、数据删除语义、回收站保留期、具体按钮形态尚待深度讨论。

## 1. UI-B05｜图1：下拉菜单和全局滚动条应按需显隐

### 用户截图/问题
`image(20261025-135552).png`：完整文件架右上「…」操作菜单较长，用户用红色矩形圈出右侧**一直存在的灰色竖滚动条**。他明确要求：滚动条**不常驻**；只有鼠标进入/靠近对应滚动边缘或在这个区域滚动时显示。用户说“所有像这种滚动条”，意味着应抽象成统一滚动体验而非只修改一个菜单。

### 已明确的目标
- 无滚动活动、无靠近/焦点时，弱化或隐藏轨道和滑块；内容完全可读。
- 本区域滚轮、触控板、键盘滚动或鼠标靠近右侧时，轻量显示滑块。
- 退出或短暂无动作后柔和淡出；不要永远占据视觉空间。
- **不能出现滚动条显隐导致菜单横向缩放或内容跳位**。不能为了藏滚动条破坏原生滚动/键盘/可访问性；系统强制显示滚动条、高对比与无动画偏好要尊重。
- 与文件架切换菜单、搜索列表、管理中心、其它长菜单和文件列表保持视觉规范一致；按场景验证，并非一刀切强行隐藏所有 OS 滚动条。

### 当前源码核实
- `apps/desktop/src/components/ShelfMenu.tsx` 基于 Radix DropdownMenu。
- `apps/desktop/src/style.css` 包含 `.shelf-menu { ... overflow-y:auto; ... }`；另有 `.file-scroll` 和 `.manager-table-scroll` 对滚动相关样式处理。
- 真实显示还受 Windows/WebView2 的 overlay/native scrollbar 行为影响；**只用 CSS 可能无法完全保证所有系统主题上的一致性**。须先验证实际渲染，再选稳定做法；不必为美术改动引入重型滚动库。

### 候选验收
1. 多条长菜单可正常从首项滚动至末项，滚动时滑块可见。
2. 静置/鼠标远离时无突兀的常驻粗灰滚动轨道。
3. 快速鼠标进入边缘时能预期抓住滑块；键盘仍可操作，焦点不丢失。
4. 宽度不跳动、不截断文本；Win10/11、125%/150% DPI、多种 Windows 滚动条偏好均须验收。

**状态：用户目标明确；具体轨道宽度、显示持续时间/透明度及平台实现仍为待验证参数。**

## 2. UI-B06｜图2：文件移动/删除造成“引用失效”，缺少可见的清理闭环

### 用户截图/问题
`image(20261025-135601).png`：文件架名 `bound-target`，前两张卡片均显示「引用失效」（图示文件名有截断），红框圈出这两张卡片。用户反馈：真实文件被移位/删除后，这些原有卡片依然留存，无法方便地删除、清理或更新，导致界面长期被无效记录占据；希望增加**删除/更新/回收站**等功能。

### 区分真实现状与 UI 可发现性
检查 PR #35 当前代码发现：
- `apps/desktop/src/App.tsx` 已明确将 `missing` 展示为「引用失效」，并有详情页**重新定位文件/文件夹**动作（仅部分普通引用）、「刷新文件状态」、普通引用移除菜单项、Delete 快捷键（只在非绑定架允许）。
- `apps/desktop/src-tauri/src/store.rs` 的 `relink_reference` 会原子更新某条普通引用并保留其 ID/标签/排序，限制重复合并；`remove_reference` 会直接 `DELETE FROM items`，**绑定目录（`kind='bound'`）禁止通过它删除**，提示本阶段无实体删除功能。
- 因而不能错误描述为“当前没有任何刷新/移除/重新定位逻辑”。真实痛点是**当前截图里的绑定架和普通引用行为不同、入口隐蔽、且没有回收/撤销与批量清理的完整闭环**。

### 候选轻量交互设计（未全部确认）
- **引用失效卡片**采用低对比状态警示 + 易发现的操作：选中时直接在现有选择工具条（或卡片内极轻量 hover 区）出现 `更新引用`、`移入回收站`；多个失效引用可选后批量清理。不依赖右键菜单或第二层管理窗口。
- **更新引用**：先查原路径是否恢复；用户可手动选择新的对应文件/目录并核验；仅在安全且唯一匹配时尝试智能重连，不盲扫整个磁盘；原卡片身份、标签和顺序应保留。
- **清理**：默认是**把工作站中的引用记录移入内部回收站**，从当前文件架隐藏，允许撤销/恢复/按需永久删除 *记录*。不可把“删除引用”悄悄升级成对源磁盘执行删除。
- **图2是 bound-target，尤其需要单独方案**：绑定架的数据既涉及 SQLite 索引也涉及真实目标目录，用户移走/删除文件后出现过期记录；建议支持非破坏性的**同步目录 / 对比真实文件状态 / 归档过期记录到内部回收站**，避免盲目对磁盘删除、重命名或更新绑定根路径。具体是否主动同步、是否保留历史记录由用户确认。
- 如将来明确需要磁盘物理删除，必须额外设计**发送至 OS 回收站（非永久删除）**的独立可识别高风险命令、权限、冲突校验和失败回滚，**绝不可混为常规“移除引用”**；目前用户没有明确授权对原文件执行系统级删除。
- **推荐最少弹层**：操作在当前文件架完成，成功显示小型 `已移入回收站 · 撤销` 反馈，而非要求进入管理中心。

### 后端工程危险点（Codex 只作评估，不立即实施）
- 原 schema `PRAGMA user_version=1`，表 `shelves`, `items`, `jobs`，有主外键关系；真实回收站如采用软删，需要显式迁移版本、旧版本兼容、状态持久化与原子恢复，不可直接把旧记录硬删后假装可恢复。
- 拷贝任务、缩略图缓存、选中项/预览详情、每个窗口的视图状态和多窗口事件通知，需要在状态变更时一致更新；SQLite ID / 约束和并发要特别检验。
- 绑定根路径不可用、单个文件丢失、路径重定向、同名不同文件、同一素材多引用、外部软件重命名导致的情况须区别处理，不能靠文件名猜测重连。
- 原生文件拖放期间冻结目标，清理/删除不得改变正在接收的文件架归属和窗口几何；不可自动删除源文件/剪贴板。

**状态：用户明确提出更新、清理、回收站需求；建议工作站内部软删除是安全候选，不意味着用户已最终确认“只删引用不删实体”的全部语义。**

## 3. UI-B07｜图3：文件架下拉菜单直接移除/回收，避免多一层界面

### 用户截图/问题
`image(20261025-135723).png`：文件架切换菜单含 `灵感收集`、`本次中转`、`bound-target`、`测试01` 等条目，用户在红框中标出了自建的 `测试01`。用户说明创建后无法直接清理文件架、不希望右键删除、不想为删除再多打开一层，想在**这个切换菜单的这一行**快速操作。

### 当前源码核实
- `apps/desktop/src/App.tsx` 文件架菜单由 `DropdownMenu.RadioGroup` / `RadioItem` 渲染，只支持切换、新建、绑定、打开独立窗口；**无同一行“删除/移入回收站”入口**。
- `apps/desktop/src/backend.ts` Backend 提供 `createShelf`、`copyReferences`、`desktopDetach/Merge` 等；截至本次检查，**没有公开 shelf recycle/restore API**。
- `apps/desktop/src-tauri/src/store.rs` 有创建和绑定文件架记录、引用删除，但在已检查代码中未发现完善的 shelf lifecycle 回收/恢复闭环。

### 候选交互方案（符合用户明确的轻量诉求）
- 文件架切换列表中，当前行**鼠标悬停或键盘聚焦**时，在右侧出现极轻量垃圾桶图标；默认其他行不常驻垃圾桶。勾选状态与图标不能重叠；点击行本体继续切换，点图标只处理本行，阻断 RadioItem 的选择事件。
- 轻量即时操作优先：**移入工作站回收站**，当前菜单中该行消失或淡出，当前窗口安全切换到其他合法可用架，并在原窗口展示**可立即撤销**的短时操作反馈。不能为普通操作强制打开完整管理中心。
- **“移除文件架”与“删除磁盘文件”分离**：普通持久架和会话架可进入内部回收站，保留其文件引用/标签/排序以供恢复；`bound` 架应是“解除文件夹绑定（不删除该真实目录和文件）”或另一明确动作，不允许偷偷删除根文件夹。
- 架含多个文件、正在复制、当前窗口独立于 Dock、架是当前活动目标、用户只剩最后一个文件架等情况，需要明确安全方案与回退目标；**不因删除正在处理的目标产生不一致或误复制**。
- `灵感收集`、`本次中转` 看似预置架（schema 初始化确实插入 ID 1/2）；**是否允许用户删除、隐藏、重置**需独立确认，不能假设完全一样。
- 回收站要有恢复和最终清理入口，但不能要求用户每次删除都多开一层。可考虑切换菜单底部加**非侵入式「最近移除 / 回收站」入口**，平常仍精简；这只是候选，不作为本轮已确定布局。

### 非破坏性状态与风险
- 回收/恢复架必须处理 `items` 和 `jobs` 外键关联（最好不改变 shelf ID）、视图记忆、Dock 顺序/展开态、浮动入口、独立窗口及主窗口活跃架。
- 任何当前进行中的复制 / DragSession 对应目标架应限制移除或让任务先受控结束；保留来源数据完整性、取消可恢复和跨版本回滚。
- 数据库版本与历史记录兼容：先规划保留关联身份的可逆软删除，避免先 `DELETE FROM shelves` 触发失败/级联导致无法恢复。
- Windows 真实物理文件删除不在本轮授权范围；如用户确实需要，须另开安全性强的产品决策。

**状态：用户已明确「菜单本行可直接删除/清理」「不要右键或新开大页面」「有回收站」的方向；具体回收站范围和预置/绑定架例外待确认。**

## 4. 建议设计推进顺序（不是 Codex 提示词）

1. **优先确认删除范围/回收语义**：用户说的删除文件架，是仅移出工作站、保留真实磁盘文件，还是包含物理文件操作？**这需要一次一个问题地确认，不能猜测。**
2. 在这一语义前提下，一次性定稿「失效卡片」「普通架」「绑定架」统一的行内操作和撤销反馈，避免碎片化页面。
3. 再设计回收站入口及默认数据保留策略，考虑多架恢复与软删除数据库规则。
4. 最后以**单个真实 Windows 样机**一起验收新菜单的按需滚动条、行内删除、软删撤销、引用修复和布局完整性，而不分成许多无意义的小版本。

## 6. 已确认决策：回收范围选择 B（工作站记录回收 + 单独的 Windows 实体回收）

用户明确在 A「仅软件记录回收」和 B「同时支持软件记录回收及独立的 Windows 真实文件回收」之间选择 **B**。此项为**已确认的产品决策**，不是候选方案。

### 两类独立操作

**1.「移入柠猫回收站」**（软件记录级、默认清理）：
- 清理单条/多条引用卡片或文件架记录，使之不再占据日常视图；可撤销、可恢复（软删除/生命周期持久化，具体 schema 与恢复保留期仍待工程设计）。
- 不改变磁盘中的真实文件或文件夹；无论是普通引用架还是绑定真实目录架，都不能把“清理工作站记录”暗中变成实体删除。
- 文件架移除仍要保障其子项、任务、布局、Dock、独立窗口与多窗状态可恢复且一致；操作默认在原菜单/卡片界面完成，不强迫右键或多开管理页。

**2.「移入 Windows 回收站」**（真实文件级、独立明确命令）：
- 必须是用户**主动选择的另一项操作**，不能与普通「移入柠猫回收站」共用不加区分的垃圾桶；应使用清楚的文案、明显的操作区分和**额外确认**。
- 额外确认应明确展示待回收项目**真实路径、项目数量、磁盘来源/绑定目录关系、是否仍被其他架引用**及操作影响；执行前必须复核实际文件存在性、目录边界和权属，不能以文件名猜测目标。
- 必须调用 Windows 回收站语义而**不是永久删除**（禁止直接等同 `fs::remove_file`/`remove_dir_all`）；失败必须报告且不得将尚未回收的实体误标记为成功。系统回收站是否能恢复、恢复后引用是否自动可访问需要独立验证。
- **一切源文件保护规则持续有效**：用户未授权任何自动清理真实文件，不允许后台扫描后自动物理回收、绑定目录根级连锅端、跨磁盘扩散或绕过额外确认。必须处理原始素材被多个文件架引用的情形。
- **失效引用**：如果路径已不存在，就只能更新/重联或清理记录，不能把不存在的实体“成功回收”。
- UI 尽量轻量：用户不必为一般清理打开第二个管理窗口；**额外安全确认仅适用于真实文件回收**，并不是用户反对的繁琐日常界面流程。

### 仍未确定，必须先问用户而不能自行实施

**关键安全边界：真实文件回收是否允许对「普通引用架中的外部源文件」执行？** 安全推荐是优先只允许在有明确受控目录边界且可核验的场景处理真实实体；引用原始素材默认只允许清理记录，除非用户再次明确授权源文件删除能力。该问题要以一次一问确认，不能把用户选择 B 解读为已批准任意磁盘路径可回收。

其他未冻结参数：Windows 回收站恢复方式、软件内部回收站入口/保留期限、重连失败处理、与多架引用共享关系的冲突、确认层级、批量回收粒度与落地 API。

### 执行和验收护栏

- 仅设计记录，**不要立即添加系统级文件删除 API**，不要直接在活跃 PR #35 修改数据模型或合并；必须先设计回滚/迁移、Windows Explorer/多架/失效链接/绑定复制/误操作恢复等真实测试。
- 已有 `Store::remove_reference` 是普通引用硬删除、绑定目录被禁止，并非可恢复软件回收站，不要将现状误标为已实现。
- 不可把「移入 Windows 回收站」等同于「从文件架隐藏记录」，二者必须是清楚区分的路径。

**状态：用户已明确确认“双层回收 B”，工作站级与 Windows 实体级动作名称/安全区分已冻结；实体文件操作具体允许范围和技术/界面细节仍待讨论。**

## 7. 已确认：Windows 实体回收范围选择 B（绑定目录和外部引用源文件都可主动回收）

用户在 A「只允许绑定目录内真实文件」与 B「绑定目录内文件及普通引用架指向的外部真实文件，均可在主动选择与额外确认后送入 Windows 回收站」之间，明确选择 **B**。

### 正式产品决定：不再将外部引用文件一律排除

- **绑定目录内的真实文件**：用户明确选择「移入 Windows 回收站」并额外确认后，可回收被选中的合法真实文件。
- **普通引用架里的外部源文件**：同样允许用户明确选择「移入 Windows 回收站」，通过额外的实体删除确认后才对真实来源路径执行 Windows 系统回收站操作。**不能把用户选择 B 误读为“外部文件永远只清理引用”。**
- **与「移入柠猫回收站」严格区分**：默认日常清理仅软回收工作站内引用/文件架记录，磁盘实体不动；“移入 Windows 回收站”必须由用户有意识地另行选择，视觉文案、效果和权限不同。两种操作不能共用一个无歧义说明的普通垃圾桶点击结果。
- **确认至少包括**：真实绝对路径、条目数、来源类型（绑定目录/外部引用）、是否有其他文件架引用相同真实路径、文件是否仍真实存在，清楚提示“该操作会影响电脑上使用这一文件的其他软件与项目”。
- **不得自动执行**：文件失效扫描、重新定位、整理文件架、刷新目录、批量删除失效引用、删除文件架等操作，不得隐式触发 Windows 实体回收；普通引用卡片的清理仍遵守记录级可恢复默认行为。
- **Windows 原生回收站语义**：不得将操作实现为 Rust `remove_file` / `remove_dir_all` 等永久删除。若目标卷或环境不支持回收站、目标已经不存在、权限不足或重解析路径验证失败，应清楚拒绝或提示失败，不得**静默降级为永久删除**。
- **保护安全边界**：执行前重新核验真实路径、普通文件与目录边界、符号链接/Windows 重解析点、目标变更和竞态；禁止误操作绑定目录根路径、工作站数据库目录、安装目录或其他高风险目录。对大批量及目录递归回收需有独立确认和保守边界，不允许仅凭一张过期索引记录永久改动未知路径。
- **多架引用与状态**：一次真实实体回收可能使多个文件架的同一路径引用同时失效；必须显式反馈并准确同步状态，不得伪装成各架仍可打开。用户尚未决定「关联引用在实体回收成功后自动移入柠猫回收站，还是保留标记为失效」，该交互留待下一轮确认。
- **回收成功后**：确认 Windows 接口返回相应成功/失败状态，再更新软件数据库与 UI；不能把 Windows 系统回收站和柠猫内部回收站混淆，不能承诺 Windows 恢复后自动恢复所有旧引用，需设计和验收。
- **路径可迁移与测试**：P0/P1 安全保源逻辑是默认引用/复制操作的约束，用户现在明确授权一个**独立且显式确认**的实体回收能力，而非改变默认复制、拖拽或清理语义。设计需提供可回滚数据库迁移、自动化沙箱文件测试以及 Windows 真实回收站验收和错误/恢复路径测试，保护仍在运行的复制任务/原生 DragSession。

### 下一项关键待决

当一个实体文件被送入 Windows 回收站后，其路径在**其他文件架里也有引用**，这些记录应：
- A：**保留并显示「引用失效」，提供重新关联/工作站回收入口**（更保留用户组织数据和标签）。
- B：**关联引用自动一起移入柠猫回收站**（界面更干净，但影响范围更广）。

必须向用户逐项确认，不能自行替用户做决定；即使用户选自动清理，也需要确保预览真实影响范围。
